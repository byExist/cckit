# mdlint 훅의 "이번 편집분만 고치기" 지시가 프롬프트 텍스트에만 의존한다

- **유형**: 개선(Enhancement) / 기술 부채
- **대상**: `plugins/mdlint/hooks/markdownlint.py`
- **우선순위**: 중간 — 오작동이 아니라 재량이 필요한 상황에서 신뢰도가 떨어지는 문제

## 배경

mdlint는 Claude Code용 플러그인으로, md 파일이 `Edit`/`Write`/`MultiEdit`로 편집될 때마다 `PostToolUse` 훅(`plugins/mdlint/hooks/markdownlint.py`)이 `markdownlint-cli2`를 그 파일 전체에 대해 실행하고, 결과를 에이전트에게 컨텍스트로 주입한다.

이 플러그인은 report-only로 설계되어 있다. 파일을 직접 고치지 않고, lint 결과에 "지시문"을 덧붙여 에이전트에게 넘긴 뒤 판단은 에이전트에게 맡긴다. 위반이 발견됐을 때(`exit code 1`) 훅이 주입하는 문구는 다음과 같다.

```text
markdownlint found issues in {path}. They cover the whole file, not only the
lines just edited: fix what this edit introduced, and leave pre-existing
violations alone unless the user asks.
{markdownlint 출력 전체}
```

즉 "위반 목록은 파일 전체 기준이니, 이번 편집이 새로 만든 위반만 고치고 원래 있던 위반은 건드리지 말라"는 것이다. 이 설계 자체는 합리적이다. 에이전트가 한 문단만 고치러 왔다가 파일 전체의 레거시 lint 부채를 "친절하게" 청소해버리는 범위 이탈(scope creep)을 막기 위한 안전장치이기 때문이다.

## 조사 내용

`markdownlint.py` 전체와 `hooks/hooks.json`, `.markdownlint-cli2.jsonc`, `README.md`를 읽고, 코드가 문서화된 대로 동작하는지 실제로 검증했다.

1. **설정 병합 순서 검증**: 스크립트 주석(9~11번째 줄)과 README는 "`--config`로 넘기는 base 설정 위에 프로젝트의 `.markdownlint-cli2.jsonc`가 markdownlint-cli2 자체 디스커버리로 겹쳐지므로 프로젝트가 항상 이긴다"고 설명한다. 임시 디렉터리에 base 설정과 프로젝트 설정을 각각 만들어 `markdownlint-cli2 --config base.jsonc :file.md`로 직접 실행해보니, 프로젝트 설정이 base 설정을 실제로 덮어썼다(base에서 끈 규칙을 프로젝트가 다시 켜자 그 규칙이 살아났다). 문서와 코드가 일치함을 확인했다.
2. **exit code 분기 검증**: 스크립트는 `exit 1`을 "lint 위반", 그 외 비정상 종료를 "도구 자체 장애"로 구분한다(67~88번째 줄). 문법이 깨진 JSONC 설정, 존재하지 않는 설정 파일 경로로 각각 실행해보니 둘 다 `exit 2`가 나왔고, 정상 위반 케이스는 `exit 1`이 나왔다. 분기 조건이 실제 markdownlint-cli2(v0.23.2)의 동작과 일치한다.
3. **콜론 프리픽스 경로 처리 검증**: 훅은 파일을 `f":{path}"` 형태로 넘겨 glob 해석을 막는다. 대괄호, 괄호, 공백이 섞인 경로(`weird[dir]/file (draft).md`)로 실행해도 glob으로 오해석되지 않고 정확히 그 파일만 대상이 되는 것을 확인했다.

세 가지 모두 "혹시 버그가 아닐까" 싶었던 지점이었지만, 실험 결과 코드와 문서가 정확히 일치했다. 그 과정에서 정작 코드 구조상 실제로 허술한 지점이 하나 드러났는데, 아래 "문제" 항목이다.

## 문제

52번째 줄에서 훅이 `tool_input`에서 읽는 값은 `file_path` 하나뿐이다.

```python
path = data.get("tool_input", {}).get("file_path", "")
```

하지만 `Edit`의 `tool_input`에는 `old_string`/`new_string`이, `MultiEdit`에는 편집 목록(`edits`, 각각 `old_string`/`new_string`)이 이미 들어 있다. 즉 "이번 편집이 정확히 어느 줄을 건드렸는지"를 계산할 수 있는 정보가 훅 호출 시점에 이미 손에 쥐어져 있는데, 지금 코드는 그걸 전혀 쓰지 않고 버린다.

그 결과 "이번 편집분만 고치라"는 규칙은 순수하게 프롬프트 텍스트 한 문장에만 의존하게 된다. 검증 가능한 구조적 신호(예: "N번째 줄부터 M번째 줄 사이의 위반만 표시")가 아니라, 에이전트가 자기 편집 내용을 스스로 되짚어 파일 전체 위반 목록과 대조한 뒤 알아서 걸러내야 하는 구조다.

## 실패 시나리오

레거시 문서 하나에 MD013(줄 길이), MD024(중복 헤딩) 등 기존 위반이 30여 개 쌓여 있다고 하자. 에이전트가 그중 한 문단만 `Edit`으로 고쳤는데, 그 문단 근처에 기존 위반이 몇 개 섞여 있다. 훅은 파일 전체의 위반 30여 개를 한 덩어리로 넘기고 "이번 편집분만 고치라"고 텍스트로만 지시한다. 에이전트는 자신이 어느 줄을 편집했는지 정확한 줄 번호로 기억하지 못하는 경우가 많고(특히 `MultiEdit`처럼 편집이 여러 군데 흩어져 있거나, `replace_all: true`로 동일 문자열이 여러 곳에서 바뀐 경우), 다음 두 실패 중 하나가 벌어질 수 있다.

- **과잉 수정**: 편집 지점 근처의 기존 위반을 "이번에 내가 만든 것"으로 착각해 고쳐버려, 사용자가 요청하지 않은 범위까지 diff가 번진다.
- **과소 수정**: 반대로 이번 편집이 실제로 만든 위반을 "원래 있던 것"으로 오판해 그대로 방치한다.

두 경우 모두 스크립트 상단 docstring이 명시한 설계 의도("에이전트가 손대지 않은 파일의 기존 위반을 대량으로 정리해버리는 것을 막는다")를 정확히 빗나가는 결과다. 문제는 이 실패가 재현 가능한 버그가 아니라 확률적으로 발생한다는 점이라, 테스트로 잡아내기도 어렵고 리뷰에서 "이번에 왜 이 줄까지 고쳤지?" 식으로 드러난다.

## 검토한 대안

**1) 현행 유지(프롬프트 지시만으로 스코핑)** — 구현 비용이 0이라는 장점은 있지만, 위에서 서술한 실패 시나리오를 그대로 안고 간다. 이번 조사의 출발점이 된 상태이므로 기준선으로만 남겨둔다.

**2) 훅이 편집 범위를 계산해 위반을 "이번 편집분"과 "기존 것"으로 나눠 표시** — `Edit`/`MultiEdit`의 `old_string`/`new_string`으로 편집 전 내용을 재구성하고, 편집 후 파일과 비교(`difflib` 등)해 실제로 바뀐 줄 범위를 구한다. markdownlint-cli2 출력은 `path:line[:col]` 형태라 정규식으로 줄 번호를 뽑아낼 수 있으므로, 그 범위(및 MD012/MD022처럼 인접 줄에 걸친 규칙을 위한 약간의 여유 버퍼) 안에 있는 위반과 밖에 있는 위반을 나눠서 각각 다른 문구로 제시할 수 있다. `Write`처럼 파일 전체를 새로 쓰는 경우나 범위 계산이 애매한 경우(예: `replace_all`로 문자열이 여러 곳에서 바뀐 경우)에는 지금처럼 전체 목록 + 텍스트 지시로 안전하게 폴백하면 된다. 구현·유지보수 비용이 늘어나고 범위 계산 로직 자체에 버그 여지가 생기는 것이 단점이지만, "지시가 지켜지길 바라는 것"에서 "구조적으로 구분해서 보여주는 것"으로 바뀌는 게 핵심 이득이다.
**3) `markdownlint-cli2 --fix`로 수정 가능한 규칙은 훅이 직접 고치기** — 스코핑 문제를 프롬프트 판단에서 아예 걷어낼 수 있다는 점은 매력적이지만, README와 플러그인 설명에 명시된 "report-only, 파일을 절대 수정하지 않는다"는 설계 원칙과 정면으로 충돌한다. 게다가 `--fix`도 결국 파일 전체 단위로 동작하므로 "이번 편집분만"이라는 범위 문제 자체는 그대로 남는다. 이번 이슈의 스코프를 벗어나는 더 큰 설계 변경이라 채택하지 않는다.

## 권장안

대안 2를 제안한다. 정확한 구현(diff 알고리즘 선택, 버퍼 크기, `replace_all`·`Write` 처리 방식)은 이 티켓을 담당하는 사람이 설계하되, 최소한 다음 방향은 유지했으면 한다.

- 범위 계산에 실패하거나 애매한 경우(Write, replace_all 등)에는 현재 동작(전체 목록 + 텍스트 지시)으로 폴백해 회귀를 만들지 않는다.
- 범위가 명확히 계산되는 경우에만 "이번 편집분" / "기존 위반" 두 그룹으로 나눠 표시한다.

## 완료 조건

- [ ] 단일 `Edit`으로 파일 일부만 바꾼 경우, 편집된 줄 범위 안의 위반과 밖의 위반이 훅 출력에서 구분되어 표시된다.
- [ ] `MultiEdit`(여러 군데 편집)에서도 각 편집 범위가 올바르게 합산되어 반영된다.
- [ ] 범위 계산이 불가능하거나 신뢰할 수 없는 경우(`Write`, `replace_all: true` 등) 현재의 "전체 목록 + 텍스트 지시" 동작으로 안전하게 폴백한다.
- [ ] `plugins/mdlint/hooks/` 아래에 새 동작을 검증하는 테스트가 추가된다(현재 이 훅에는 전용 테스트가 없다).
- [ ] `README.md`의 동작 설명이 갱신된다.
